# Phase 0 录音采集协议（20 段 × 3 路由）

Phase 0 的门禁是硬的：**没有实测表就不进 P1**，也不许用估计值代替。表有 60 格（20 段素材 × 3 条输出路由），这张表的价值全在采集质量上——素材不对，测出来的数字只是把错的场景测得更精确。

这份协议只解决一件事：让素材到手后，一条命令就能把表填满，而不是手工抄 60 行。

## 一分钟版

1. 把音频放进 `bench/fixtures/recordings/`，命名 `rec-01.wav` … `rec-20.wav`；
2. `pnpm bench:latency:collect --list` 检查命名与缺段；
3. 依次把系统输出切到内置扬声器 / 有线 / 蓝牙，各跑一次：

```bash
pnpm bench:latency:collect --routes built-in
pnpm bench:latency:collect --routes wired
pnpm bench:latency:collect --routes bluetooth
```

4. 打开 `bench/reports/<date>-phase0-latency.md`，看表格、缺口与 §f.3 门禁判定。

## 音频规格

| 项 | 要求 | 原因 |
|---|---|---|
| 采样率 / 声道 | 16000 Hz、单声道 | 采集链路与 ASR 的固定输入 |
| 位深 / 编码 | PCM16，WAV format tag 1 | 解码器只认这个 |
| 头部 | 44 字节标准头（数据从第 44 字节起） | 解码器用 `requireCanonicalHeader` 校验，非标准头会被判为不可用 |
| 时长 | 单段 3–8 秒 | 太短测不出端点，太长单次测量成本高 |
| 尾部 | 结尾留 ≥ 600 ms 静音 | VAD 需要 400 ms 静音才能确认端点；以语音结尾的片段会被判 `blocked` |

转换命令（任意来源 → 规格内）：

```bash
afconvert -f WAVE -d LEI16@16000 -c 1 in.m4a rec-01.wav
```

`bench/fixtures/recordings/` 已在 `.gitignore` 里：**这是个人语音数据，永远不提交**。

## 20 段怎么分

每段都要有明确的测量用途，不要录 20 段一样的「今天天气不错」。

| 段号 | 内容 | 覆盖的指标 |
|---|---|---|
| rec-01 – rec-10 | 双人自然对话，各 5–8 轮，正常语速 | M5 十轮不丢上下文、M1 基础样本 |
| rec-11 – rec-13 | 对话中一方**打断**对方（插话） | M3 打断响应、M6 打断后重述率 |
| rec-14 – rec-15 | 一段长停顿（>1.5 s）后再继续 | 端点误触发（VAD 把停顿当说完） |
| rec-16 – rec-17 | 外放回声场景：扬声器出声时对方继续说话 | M4 / M7 回声误触发 |
| rec-18 | 中英混说一句（如「明天 ten 点开会」） | ASR 终稿稳定度 |
| rec-19 | 安静房间 + 明显底噪，各半段 | 端点阈值在噪声下的偏移 |
| rec-20 | 结尾刻意留 1 s 静音的正常单句 | 端点测量的基准对照 |

**M1 的「停说 → 出声」不能只靠脚本**：脚本给的是四段 P50 相加，真人听感要靠播放录音逐段打点校准，把校准值单独记在表外，不要覆盖脚本产出的数字。

## 三条路由不是录三遍

路由指的是**声音从哪出去**（内置扬声器 / 有线 / 蓝牙），影响的是 TTS 首包、回声与播放启动，不影响输入侧的端点、ASR、LLM。所以：

- 同一份 20 段素材，在每条路由下各跑一次采集；
- 每次跑之前先切系统输出设备，跑完在报告里核对「默认输出设备」一栏；
- 路由是**操作者声明**的，脚本只能记录设备名，证明不了声音真的从那里出去。这条写进了报告的读数注意里，别把它当成已验证。

这台机器当前默认输出是「小爱音箱-6060」，不是内置扬声器。不先切设备就开跑，三条路由测的是同一条。

## 机器能测什么、不能测什么

| 列 | 测量方式 | 现在能不能测 |
|---|---|---|
| 端点 | 离线 VAD 复算：最后一个语音帧 → 静音满 400 ms 的确认帧 | **能**，不依赖麦克风与模型 |
| ASR 终稿 | 现有批处理路径跑该段素材的墙钟时间 | 需 `pnpm setup:asr`（构建 `transcribe-cli`） |
| LLM 首 token | sidecar `stream:true` 首个 `delta.content` | 需本地 `.gguf`（安装包不内置） |
| TTS 首包 | 隐藏窗口 `speechSynthesis` 的 `onstart` | 需解锁 + 有可用语音（`voices>0`） |
| M1 | 四列 P50 相加 | 能算，但必须用听感值校准 |
| M4 / M6 / M7 | 误触发率与重述率 | **不能**，只能人耳计数后填进 `--` 参数 |

端点这一列是本轮新增的：它把「VAD 结构延迟」从配置里的 400 ms 变成了每段素材各自的实测值（含迟滞尾巴）。但它是**下限**——真实「停说瞬间」落在最后一个能量帧内部，离线无法知道，所以表里不写估计值，只写实测。

## 填表规则

- 空格写 `待填`：素材还没到；
- 测不到写 `blocked` + 原因：前提缺失，不是 0；
- **任何格子都不许填估计值**。这张表是 P1 的门禁，一个估出来的格子会把门禁悄悄作废。

跑完之后，报告里同时给出 §f.3 六条硬降级的机械判定（`F1`–`F6`）。`未测` 不等于「未触发」：关键规则缺数据时，`allowL2` 是「未判定」，界面也不许出现「实时对话」措辞。

## 常见错误

| 现象 | 原因 |
|---|---|
| 文件名被忽略 | 不是 `rec-NN.wav`（两位数字），或段号 > 20 |
| 整段被判 `blocked`：VAD 未确认端点 | 结尾静音不足 400 ms |
| 整段被判 `blocked`：音频不可用 | 采样率/声道/头部不合规，用上面的 `afconvert` 重转 |
| TTS 全部 `blocked`：`voices=0` | 锁屏，或系统没有可用中文语音 |
| 表格里三条路由的输入侧数字一样 | 正常：输入侧与路由无关，只有 TTS 首包逐路由不同 |
